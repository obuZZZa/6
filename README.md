## 1. Общие положения

Настоящий Регламент определяет порядок подготовки, проверки, выпуска, распространения и установки обновлений мобильного приложения «Метеодневник здоровья», включая Android-клиент, серверный API, базу данных PostgreSQL, погодный сервис и push-уведомления.

Цели Регламента: исправление ошибок, устранение уязвимостей, поддержание совместимости компонентов, сохранение пользовательских записей и контроль безопасной эксплуатации.

Регламент распространяется на разработчиков, релиз-менеджера, администратора, специалиста по информационной безопасности и пользователей приложения.

## 2. Термины и определения

- **Обновление** — новая версия приложения или компонента, устанавливаемая поверх предыдущей.
- **Релиз** — зафиксированный набор изменений, выпускаемый как единая версия.
- **Патч (hotfix)** — внеплановое обновление для устранения критической ошибки или уязвимости.
- **Миграция** — изменение структуры PostgreSQL или преобразование данных при обновлении.
- **Обратная совместимость** — способность новой версии работать с прежними данными и API.
- **SemVer** — семантическое версионирование в формате `X.Y.Z`.
- **Окно обслуживания** — согласованный интервал проведения работ.
- **Откат** — возврат к предыдущей рабочей версии при сбое.

## 3. Виды и периодичность обновлений

Обновления делятся на плановые и внеплановые. Плановый выпуск выполняется раз в 2–4 недели после завершения тестирования. Внеплановый выпуск выполняется в срочном порядке при критической ошибке, потере данных или уязвимости безопасности.

Используется SemVer:

- `X` — мажорная версия при обратно несовместимом изменении API или формата данных;
- `Y` — минорная версия при добавлении функциональности с сохранением совместимости;
- `Z` — патч при исправлении ошибок без изменения API.

Текущая версия продукта: `1.0.0`. Плановое окно обслуживания: рабочие дни с 20:00 до 23:00 по московскому времени. Критические hotfix выпускаются вне окна после согласования релиз-менеджером.

## 4. Обновление клиентской части

### 4.1 Сборка и подпись Android-клиента

1. Проверить номер версии и `versionCode`.
2. Выполнить `./gradlew test lint assembleRelease`.
3. Подписать APK или AAB ключом из защищённого хранилища CI/CD.
4. Проверить контрольную сумму артефакта.

```bash
./gradlew clean test lint bundleRelease
sha256sum app/build/outputs/bundle/release/app-release.aab
```

Keystore не хранится в репозитории. Для корпоративных устройств допускается распространение подписанного APK через MDM. Для публичного выпуска используется Google Play или RuStore.

### 4.2 Тестирование и публикация

Сборка проходит внутренний трек, затем закрытый трек магазина. Поэтапный rollout: `10% → 50% → 100%`. При росте ошибок rollout приостанавливается. В описание релиза включаются изменения, исправления, ограничения и минимальная версия Android.

## 5. Обновление серверной части

Обновление выполняется по согласованному графику с предварительным уведомлением о кратковременной недоступности сервиса. Сначала обновляется API, затем фоновые задачи и конфигурация уведомлений. Образы фиксируются тегом версии; использование `latest` в продуктивной среде запрещено.

```bash
docker compose pull api:1.1.0 worker:1.1.0
docker compose up -d api worker
curl -fsS https://meteo.example.ru/api/health
```

После запуска проверяются авторизация, создание записи, синхронизация и получение погоды.

## 6. Обновление базы данных и миграции

Перед каждой миграцией создаётся полная резервная копия с датой и версией:

```bash
pg_dump "$DATABASE_URL" > /backup/meteo_2026-10-13_v1.1.0.sql
pg_restore --list /backup/meteo_2026-10-13_v1.1.0.sql > /tmp/backup-check.txt
```

Миграции выполняются строго последовательно. Пропуск промежуточных версий и установка версии ниже текущей запрещены. Перед миграцией проверяются отсутствие активных административных операций и свободное место не менее 30% от размера базы.

После миграции выполняются:

```bash
alembic upgrade head
psql "$DATABASE_URL" -c "SELECT 1;"
psql "$DATABASE_URL" -c "SELECT COUNT(*) FROM health_entries;"
```

Нельзя пропускать миграции `001_init`, `002_weather_snapshot`, `003_client_idempotency` и `004_medication_reminders`.

## 7. Порядок установки обновления

1. Проанализировать changelog и оценить влияние на клиент, API и БД.
2. Развернуть сборку на тестовом стенде, максимально близком к продуктивному.
3. Выполнить функциональные, регрессионные и security-тесты.
4. Согласовать готовность с релиз-менеджером и специалистом по ИБ.
5. Создать резервную копию и проверить возможность отката.
6. Установить обновление на продуктивную среду согласно плану.
7. Выполнить контрольный цикл: вход, создание записи, синхронизация, погода, уведомление и экспорт.
8. В течение 60 минут контролировать ошибки, задержку API и очереди синхронизации.
9. Зафиксировать результат в журнале обновлений.

## 8. Откат изменений

Откат выполняется при недоступности API более 5 минут, массовых ошибках авторизации, потере записей, повреждении миграции, критической уязвимости или росте ошибок мобильного клиента выше согласованного порога.

Порядок отката клиента: остановить rollout, вернуть предыдущую сборку в магазине или MDM, уведомить пользователей и проверить сохранность локальных записей.

Порядок отката сервера: остановить новый API, запустить образ предыдущей версии, проверить `/health`, восстановить БД из проверенной копии только при повреждении данных и выполнить контрольный цикл.

Миграции, удаляющие столбцы или преобразующие данные без обратного преобразования, не откатываются автоматически. Для них до выпуска обязательны backup и отдельный план восстановления.

Решение об откате принимается не позднее 15 минут после обнаружения критического дефекта.

## 9. Роли и ответственность

| Роль | Ответственность |
|---|---|
| Разработчик | Реализация, тестирование, описание изменений и подготовка сборки. |
| Релиз-менеджер | Координация выпуска, согласование окна, контроль готовности и отката. |
| Администратор | Backup, миграции, установка серверных компонентов и мониторинг. |
| Служба информационной безопасности | Проверка уязвимостей, приоритизация патчей и контроль секретов. |
| Конечный пользователь | Установка доступных обновлений и сообщение о неисправностях. |

## 10. Документирование и контроль

Все действия протоколируются в журнале обновлений. Для каждого выпуска хранятся changelog, pull request, результаты тестов, контрольные суммы артефактов, версия клиента, API и БД, а также решение о выпуске или откате.

Периодичность проверки соблюдения Регламента — ежеквартально и после каждого критического hotfix. Основные показатели: доля успешных выпусков, число откатов, количество инцидентов после обновления, время восстановления и процент актуальных клиентов.
